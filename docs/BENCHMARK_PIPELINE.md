# CORE BREAKER 벤치마크 및 봇 파이프라인

> 문서 버전: 1.0
>
> 기준 빌드: 2026-07-21 `main`

## 1. 목적

벤치마크는 다음 질문에 답하기 위한 도구다.

- 각 웨이브가 의도한 난이도 곡선을 만드는가?
- 특정 스킬 또는 LV3 진화가 생존과 클리어 시간을 과도하게 개선하는가?
- 블록 특성과 보스 패턴이 정체 구간을 만드는가?
- 동일 조건을 반복했을 때 결과 분산은 어느 정도인가?
- 봇이 규칙을 우회하지 않고 플레이어와 같은 입력만으로 공략하는가?

## 2. 실행 모드

### WATCH RUN — 기본 모드

- `/benchmark` 진입 시 기본 선택된다.
- `app/page.tsx`의 실제 게임 런타임과 Canvas 물리를 그대로 사용한다.
- 스킬 이펙트, 아이템, 보스, 웨이브 전환을 화면으로 확인한다.
- 1×, 2×, 4×, 8× 관찰 배속을 지원한다.
- 결과 메타데이터:
  - `engineVersion: live-game-runtime-v1`
  - `engineParity: exact-live-runtime`
  - `policyVersion: predictive-controls-v1`

실제 플레이와의 시각·물리 패리티를 확인할 때 WATCH RUN을 기준으로 사용한다.

### HEADLESS — 대량 실행 모드

- Canvas와 DOM 렌더링을 생략한다.
- `app/canonical-engine.ts`의 좌표 기반 120Hz 고정 스텝 엔진을 사용한다.
- 최대 8개의 Worker로 3~1,000회를 병렬 실행한다.
- 동일한 활성 웨이브 정의, 스킬 설정, 밸런스 설정과 봇 정책을 입력으로 사용한다.
- 결과 메타데이터:
  - `engineVersion: canonical-fixed-step-v1`
  - `engineParity: fixed-step-canonical-rules`
  - `policyVersion: predictive-controls-v1`

HEADLESS는 과거의 성공 확률·DPS·손실 확률 기반 집계 모델을 사용하지 않는다. 공, 패들, 블록, 아이템을 좌표 상태로 갱신한다.

다만 WATCH RUN과 HEADLESS는 현재 동일한 업데이트 함수 하나를 공유하는 구조가 아니라 실제 런타임과 렌더링 없는 규칙 엔진으로 분리되어 있다. 따라서 신규 스킬이나 블록 규칙을 추가할 때 두 경로의 패리티 테스트도 함께 추가해야 한다. 최종 판단은 WATCH RUN과 사람 플레이 검증을 우선한다.

## 3. 공유 입력

두 실행 모드는 다음 설정을 함께 사용한다.

- `app/wave-config.ts`: 활성 20웨이브 패턴과 HP 배율
- `app/skill-config.ts`: 스킬 설명, 레벨 수치, 쿨타임, 진화
- `app/balance-config.ts`: 보스 HP와 공격 주기 등 밸런스 값
- `app/bot-policy.ts`: 봇의 관찰 → 입력 정책
- 벤치마크 시드와 목표 웨이브

Stage Lab 또는 Skill Lab에서 저장한 설정은 새 실행 시작 시 읽는다. 실행 중 설정을 바꿔 기존 결과와 섞지 않는다.

## 4. 봇 권한

봇이 반환할 수 있는 값은 다음 세 가지뿐이다.

```ts
type CanonicalControls = {
  move: -1 | 0 | 1;
  aimX: number;
  aimY: number;
};
```

- `move`: 플레이어의 A/D와 같은 좌우 이동
- `aimX`, `aimY`: 플레이어의 마우스와 같은 조준점

봇은 블록 HP, 공 위치, 스킬 쿨타임, 아이템, CORE를 직접 변경할 수 없다. 정책 함수는 관찰값을 읽고 입력만 반환해야 하며, 테스트에서 관찰 전후 상태가 동일한지 검증한다.

## 5. 조준 정책

정책 버전: `predictive-controls-v1`

### 수비

1. 아래로 이동하는 공 중 패들에 가장 먼저 도착할 공을 선택한다.
2. 좌우 벽 반사를 포함해 패들 높이에서의 예상 X 위치를 계산한다.
3. 현재 패들 속도로 도달 가능한 위치를 판단해 일찍 이동한다.
4. 공을 놓칠 위험이 낮을 때만 아이템 회수를 우선한다.

### 공격

1. 살아 있고 파괴 가능한 블록만 후보로 사용한다.
2. 회복, 폭발, 가드, 반사와 블록의 Y 위치·HP를 반영해 우선순위를 계산한다.
3. 파괴 불가 블록이 직선 경로를 막으면 다른 경로나 목표를 선택한다.
4. 반사 블록은 보호된 아래 면의 중심을 직접 조준하지 않는다.
5. 좌우 약점과 벽 반사점을 이용해 측면·상단 진입 경로를 만든다.
6. 패들 예상 접촉점에 오프셋을 주어 원하는 출사각을 만든다.
7. 일정 시간 블록 수가 줄지 않으면 뱅크 방향과 목표를 교대한다.

### 안정성

- 실제 게임의 최대 조준 수평 비율과 최소 수직 속도를 지킨다.
- 무작위 정책을 제외하면 시드로부터 결정론적으로 행동한다.
- 반사 블록만 남은 배치에서도 클리어하거나 뱅크 공략 상태로 전환해야 한다.

## 6. 실행 순서

```text
활성 Wave/Skill/Balance 설정 로드
  → 시드로 게임 상태와 RNG 생성
  → 시작 스킬 1개 선택
  → 매 고정 스텝마다 관찰 생성
  → 봇이 move/aim 입력 반환
  → 게임 상태 갱신
  → 웨이브 클리어 시 보상 선택
  → 목표 웨이브, 게임 오버, 최대 시간에서 종료
  → 결과 저장 및 그래프 집계
```

## 8. 결과 해석

- HEADLESS 결과는 같은 `engineVersion`, `policyVersion`, Wave/Skill 설정끼리만 비교한다.
- 설정 또는 엔진 버전이 다른 결과는 같은 그래프에 합치지 않는다.
- 봇의 조준 개선 전후 결과는 난이도 변경이 아니라 정책 변경일 수 있으므로 `policyVersion`을 확인한다.
- 특정 스킬의 평균 도달 웨이브만 보지 말고 선택 시점, 발동 수, 피해, CORE, 클리어 시간을 함께 본다.
- 반사·파괴 불가가 많은 웨이브는 평균값 외에 최대 클리어 시간과 정체 비율을 본다.
- 3~5회는 파일럿, 20회는 방향 확인, 100회 이상은 분포 확인에 사용한다.
- 최종 난이도 결정은 WATCH RUN과 사람 플레이를 포함한다.
